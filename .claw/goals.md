# 项目目标

`goals.md` 是项目目标、范围和成功标准的唯一事实源。

## 项目愿景

构建 **CloudCC Semattice（语义格）**——面向中大型企业、完全由智能体操作的多租户业务数据与语义运行底座（Agentic Business Data Runtime）。平台以原生事务数据面承载客户自定义业务系统，以版本化语义元数据让 Agent 可靠理解和操作对象、字段、关系与业务规则；CRM 等业务能力以领域包构建在其上。平台不提供前端页面，所有业务、配置与运维均由 Agent 通过等价的 API、MCP 和非交互式 CLI 操作，并共享同一套元数据、权限、Changeset、审计和回滚协议。

## 当前范围

### In Scope Now

- Phase 0 的架构验证、工程基线和技术选型 ADR
- 多 PostgreSQL 分片下的租户控制面、128 bucket、RLS 与连接池上下文 PoC
- 元数据、Changeset、`object_record + typed index`、outbox 和受控 Agent 工具的验证
- Agent 语义闭环：业务定义、同义词、单位/枚举、关系、生命周期、数据分类、质量规则和版本证据均进入已发布元数据
- 无外部系统时的原生业务承载：客户可定义并存储对象、字段、关系和记录
- 把既有 Agent CC 运营管理端扩展为产品无关的统一租户运营控制面：Agent CC 与 CloudCC Semattice 均可单独或按任意顺序开通，并分别管理产品订阅状态；现有协议产品代码继续使用 `native_platform`
- 开通任一首个产品时由运营控制面创建或解析全局租户，安全生成 UUIDv4 `tenant_id` 及一对一 20 位 `company_id`；两个产品需要绑定时必须归属同一全局租户并复用同一标识，每个全局租户对每种产品最多一个投影
- 通过与 Agent CC 产品订阅解耦的共享身份服务或企业 IdP 复用全局主体，并由数据平台独立计算对象/字段/记录授权
- 原子能力契约、MCP 服务与面向 Agent 的非交互式 CLI PoC

### Out Of Scope Now

- Agent CC 或其他旧系统的历史业务数据、业务表、旧前端和旧插件迁移；`FEAT-011` 明确的租户身份回填和既有开户接口扩展除外
- 允许租户执行任意数据库触发器、JVM 类、原生插件或不受控网络访问
- 在 PostgreSQL OLTP 主库执行全文搜索、复杂报表或跨租户运营分析
- Web、移动端、BFF、人工交互式管理页面和带菜单/提示的 CLI
- 将完整 CRM 模块群作为平台内核验证的前置条件
- 将跨系统 Golden Record、匹配合并或主数据分发作为首期必需能力
- 直接共享、读取或写入 Agent CC 用户数据库、角色表或长期凭据
- 在 CloudCC Semattice 内重建第二套全局租户目录、自行生成租户 ID，或让两个产品直接共享运营数据库表

## 里程碑

### MVP

- [ ] 完成 Phase 0 高风险架构假设的压测与故障测试，并记录真实证据
- [ ] 形成可本地运行、受安全门禁约束的工程基线

### V1

- [ ] 既有运营开户能力可独立开通 Agent CC-only、Native-only 或双产品租户；首个产品建立统一 `tenant_id + company_id`，以后绑定的第二个产品必须复用该标识，任一产品失败不影响另一产品且不会产生第二组租户 ID
- [ ] 新租户开户不执行租户专属 DDL，目标 2 分钟内可用
- [ ] 自定义对象与普通字段无需变更业务表 DDL，并可安全 CRUD
- [ ] 所有元数据写操作均经过可预检、审批、审计和回滚的 Changeset
- [ ] 每个发布的原子能力均提供行为等价的 API、MCP Tool 和非交互式 CLI

### Later

- [ ] 多区域、自动准入与租户在线再平衡
- [ ] 搜索、OLAP、自动化、行业包和规模化商业计量

## 成功标准

| 维度 | 指标 | 目标值 |
|------|------|--------|
| 功能 | 元数据治理 | 100% 元数据写操作通过 Changeset |
| 质量 | 租户隔离 | 受信 TenantContext、强制 PostgreSQL RLS、同租户关系约束和连接池残留防护同时生效；跨租户访问成功数为 0 |
| 性能 | 普通记录读取 P95 | 300 ms 内 |
| 性能 | 普通记录写入 P95 | 500 ms 内 |
| 业务 | 租户开户 | 不执行建库、建 schema 或建分区 DDL；目标 2 分钟内可用 |
| 业务 | 统一租户运营 | Agent CC-only、Native-only 和双产品均合法；两个产品无固定先后，绑定时共享同一组 `UUIDv4 tenant_id + 20 位 company_id`；各产品操作独立幂等和审计 |
| 扩展 | 平台规模 | 通过多分片支持十亿至百亿级记录，不依赖单实例承载 |
| Agent 原生 | 能力入口一致性 | 每个已发布原子能力均通过 API、MCP 与 CLI 契约测试 |
| Agent 原生 | 语义可靠性 | Agent 仅基于已发布元数据版本理解对象/字段/关系；结果携带可复核的数据与元数据版本证据 |
| 产品 | 原生业务承载 | 在无外部数据源的验收场景中，客户可通过已发布元数据完成对象定义、记录存储、查询与审计 |
| 安全 | 身份与授权边界 | 共享身份服务或企业 IdP 的同一全局主体可访问被授权的统一 `tenant_id`；Native-only 认证不依赖 Agent CC 产品 active，跨组织、错误 audience、过期/撤销令牌与越权数据访问均被拒绝 |

## 约束

- 时间约束：Phase 0 计划 4–6 周；其余阶段以 `FEAT-009` 为路线基线
- 技术约束：逻辑 OneDatabase、物理多 PostgreSQL 分片；记录与索引分离；事务、搜索与分析分离
- 租户约束：既有运营管理端是 `tenant_id/company_id` 和全局生命周期的唯一事实源；Native 仅维护产品侧租户、配额和分片路由投影
- 隔离约束：UUID 只提供不可枚举和误命中缓冲，不替代授权；受信 TenantContext、RLS、同租户关系约束、连接池上下文清理和跨租户测试必须同时生效
- 交互约束：无前端页面；CLI 仅接受结构化输入并输出 JSON/JSON Lines，不提供人类交互菜单
- 合规约束：默认拒绝；身份、授权、审计、敏感数据最小化与数据驻留需求需在 Phase 0 明确
- 资源约束：单分片初始目标为 16 vCPU / 64 GB；最终容量阈值必须由实测校准
