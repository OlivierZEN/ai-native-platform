## Semattice 是什么

CloudCC Semattice（语义格）是一套面向智能体的业务数据与语义运行底座，产品类别是 Agentic Business Data Runtime。

它让企业和 AI 在同一套受治理模型上定义、存储、查询和保护业务数据：

- 用元数据版本定义对象、字段、关系和语义。
- 用记录运行时承载客户、联系人、订单、项目等业务实例。
- 用角色、Permission Set、数据范围、团队和共享规则控制访问。
- 用 Changeset、审批、幂等和审计约束高风险变化。
- 用统一 Capability Contract 让 AI 发现并执行原子能力。

把 Semattice 理解为业务应用下方的运行底座，而不是某一个固定业务应用。CRM、项目交付、服务管理等领域能力可以在同一个内核上构建为业务对象和领域包。

## Semattice 解决什么问题

| 问题 | Semattice 的解决方式 | 业务价值 |
|---|---|---|
| AI 不知道字段和数据代表什么 | 发布版本化的对象、字段、关系和语义快照 | AI 基于稳定业务模型设计和执行，不靠猜测表结构 |
| 每次增加业务对象或普通字段都要改业务表 | 以元数据驱动统一记录运行时 | 客户、项目、工单等模型可以按租户演进 |
| AI 能调用接口但缺少安全边界 | 令牌绑定租户与主体，叠加 Scope、RBAC、RLS、审批和审计 | AI 只能在明确授权范围内行动 |
| 业务模型变化可能破坏存量数据 | 通过 Changeset 校验、模拟、回填、覆盖率门禁和发布 | 高风险变更可预检、可审批、可追踪 |
| 多种调用入口容易行为漂移 | 从一个 Capability Registry 投影统一能力契约 | API 调用可被发现、编排和验证 |

## Semattice 不是什么

- 不是固定字段和固定流程的 CRM 成品；CRM 是可构建在其上的领域包。
- 不是以跨系统 Golden Record、匹配合并和主数据分发为首要目标的传统 MDM。
- 不是允许 AI 直连数据库、执行任意 SQL、触发器或不受控代码的平台。
- 不是 AgentCiCi、Agent CC 或 CloudCC CRM；这些都是 Semattice 的外部应用或集成方。
- 不是靠模型自行决定权限和发布结果；确定性策略、审批和审计拥有最终约束权。

## 从业务需求到平台设计

设计时按以下顺序把业务语言映射到 Semattice：

1. 找出需要长期保存和独立管理的业务实体，把它们设计为对象。
2. 把实体属性设计为字段；只有需要有界过滤的字段才考虑活动类型化索引。
3. 把实体之间的稳定引用设计为关系，不把展示文本当作关系替代品。
4. 把每个业务实例设计为记录，并明确所有者和数据组织。
5. 把岗位职责设计为角色，把可复用权限设计为 Permission Set。
6. 把“本人、部门及下级、指定组织或全租户”等可见范围设计为数据范围。
7. 把例外协作设计为直接共享、记录团队、访问组或共享规则。
8. 把模型变化设计为新草稿和 Changeset，不把已发布定义当作可直接覆盖的配置。
9. 把需要 AI 执行的动作映射到已发布原子 Capability，并核对 Scope、风险、审批和幂等要求。

如果业务需求尚不明确，先输出设计问题和候选模型，不调用写 API。只有用户要求实施、目标环境明确且授权满足时才进入调用阶段。

## 功能模块与业务场景

| 模块 | 是什么、解决什么问题 | 典型业务场景 | 实施入口 |
|---|---|---|---|
| Capability 发现 | 当前环境可调用能力的机器可读目录 | AI 首次连接、上线版本变化、实施前核对输入 Schema | `system.capability.list` |
| 租户与企业边界 | 隔离数据、元数据、授权和用量的企业运行空间 | 查询产品状态、暂停或恢复服务、调整权益、发起退役 | `tenant.*`；公开 API 不负责租户开通 |
| 元数据版本 | 对一组对象、字段和关系的一致快照 | 设计新业务应用、冻结可复核模型、保留历史兼容证据 | `metadata.version.*` |
| 对象 | 业务实体的版本化结构定义，不是业务数据本身 | 客户、联系人、订单、项目、工单、资产 | `metadata.object.upsert`，读取通过 `metadata.version.get` |
| 字段 | 对象记录中的命名属性及类型、必填、索引、唯一性和生命周期规则 | 客户名称、订单金额、项目状态、服务到期时间 | `metadata.field.upsert`，退役走字段生命周期和 Changeset |
| 关系 | 对象之间的版本化引用 | 联系人属于客户、订单引用客户、项目关联多个成员 | `metadata.relation.upsert` |
| Changeset | 对已发布模型进行受治理演进的工作单元 | 增加必填字段、建立索引、字段换名或换类型、清除旧字段数据 | `metadata.changeset.*` |
| 记录运行时 | 已发布对象的业务数据实例及有界查询能力 | 创建客户、更新订单、查询工单、软删除业务记录 | `runtime.record.*` |
| 角色与 Permission Set | 把业务职责映射为可复用原子权限 | 销售、客服、财务审核员、项目经理的功能权限 | `authorization.role.*`、`authorization.permission-set.*` |
| 对象策略与数据范围 | 决定是否执行对象/字段/记录授权，以及角色可访问哪些记录 | 仅看本人客户、查看部门及下级订单、全租户审计 | `authorization.object-policy.set`、`authorization.role.set-data-scope` |
| 共享与协作 | 在基础角色和数据范围之外提供受控协作访问 | 临时移交一条商机、项目团队长期协作、区域批量共享 | `record.share.*`、`record.team.*`、`authorization.group.*`、`record.sharing-rule.*` |
| 组织合并 | 在组织撤并时迁移数据归属、成员和层级关系 | 分公司合并、部门撤销、区域重组 | `organization.merge.*` |
| 职责冲突与访问解释 | 阻断互斥角色并说明一次授权判断的最小来源 | 申请人与审批人分离、排查“为什么能看这条记录” | `authorization.role.set-conflict`、`authorization.access.explain` |
| 用量 | 当前租户请求、执行、RU、记录和逻辑数据量的观测视图 | 容量趋势、异常增长、产品使用分析 | `usage.*`；平台物理采样不是租户账单 |

## 对象示例：从业务概念到可运行模型

业务目标：建立客户与联系人管理能力，并让销售人员只能维护自己或所在组织范围内的数据。

### 设计层

1. 把“客户”和“联系人”设计为两个对象，而不是把全部信息塞进一个 JSON 字段。
2. 为客户设计名称、客户等级等字段；为联系人设计姓名、电话等字段。
3. 从联系人到客户设计一个 `lookup` 关系。
4. 为常用的客户名称前缀查询配置文本索引；不为不参与查询的字段盲目建索引。
5. 创建销售角色和 Permission Set，并分别授予对象、字段和动作权限。
6. 为销售角色配置 `own` 或 `organization_descendants` 数据范围。
7. 对跨部门临时协作使用直接共享；对长期协作使用记录团队或共享规则。

### 实施层

1. 创建草稿元数据版本。
2. 创建客户和联系人对象，并保存稳定 `object_id`。
3. 创建字段和关系，并保存稳定 `field_id`、`relation_id`。
4. 回读整个版本，核对对象、字段和关系。
5. 在独立审批后发布首次模型；已有活动版本时改走 Changeset。
6. 配置权限集、角色、数据范围和对象策略。
7. 创建记录并回读验证元数据校验、关系和授权是否生效。

对象定义和对象记录必须区分：修改“客户对象”的标签、字段或关系属于元数据演进；修改某一个客户的名称属于记录更新。详细调用边界见 [常用操作流程](capability-workflows.md) 和 [资源模型](resource-model.md)。

## AI 的设计输出要求

用户请求产品说明、业务方案或模块设计时，输出至少包含：

1. 业务目标和待解决问题。
2. 选用的 Semattice 模块及选择理由。
3. 对象、字段、关系、记录、权限和共享的候选模型。
4. 当前能力可以实现的部分，以及尚无公开 Capability 的边界。
5. 如需实施，列出依赖的环境、稳定资源 ID、Scope、审批和验证步骤。

不要在设计回答中伪造已经创建的资源、线上状态或验证结果。用户只要求设计时，不读取令牌、不执行写操作。
